`docker compose exec backend python -m pytest <path> -v`

## Your Task — Stage: `{{current_stage}}`

### If current_stage is `happy_path_tests`

Write tests that verify the single end-to-end happy path flow the Coder implemented.
Scope is strictly: does the happy path work end-to-end with valid input?

Required test cases for this stage:
- **Setup:** Any fixtures, factories, or test tenant context needed.
  Multi-tenant tests must use `with schema_context(<schema>):` — never test
  against the public schema for tenant-scoped logic.
- **Happy path case:** The exact flow described in `architect_notes → happy_path_flow`
  runs without error and produces the expected output.
- **State assertion:** After the flow, assert the expected state changes
  (model fields, task dispatch, response shape). Do not assert implementation details —
  assert observable outcomes.

Do not write edge case or error handling tests at this stage. Those belong to
`full_implementation_tests`.

### If current_stage is `full_implementation_tests`

Extend the happy path tests to full coverage of the implementation. This includes:

- **Error cases:** Every custom error class introduced must have a test that triggers it.
- **Edge cases:** Every edge case declared in architect_notes must have a test.
- **Async task tests:** For every Celery task introduced:
  - Test that the task executes correctly when called directly (not via broker).
  - Test idempotency: calling the task twice with the same inputs produces the
    same result without side effects doubling.
  - Test the failure classification: simulate an exception and assert the correct
    failure mode behaviour (`SILENT` logs, `ALERT` notifies, `DLQ` creates a
    `DeadLetterEntry`).
- **Multi-tenancy tests:** For any tenant-scoped logic, verify that data from
  one tenant is not accessible from another tenant's schema context.
- **Permission tests:** For every new API endpoint, test that unauthenticated
  requests are rejected, and that the correct role is required.

### For all test stages

**Naming convention:**
```
test_<what_is_being_tested>_<condition>_<expected_outcome>

Examples:
test_generate_invoice_pdf_valid_invoice_dispatches_task
test_generate_invoice_pdf_missing_invoice_returns_silently
test_payment_webhook_duplicate_call_idempotent
```

**File location:**
Follow the structure declared in `backend/tests/Readme.md`. If that file is missing,
place tests in `backend/apps/<app_name>/tests/test_<module_name>.py` and flag the
missing Readme.

**After writing each test file, state:**

```

**After writing all tests, run them:**

```

Report the full output. Do not summarise — paste it verbatim.

## When Tests Fail

If tests fail because of a bug in the implementation (not the test itself):

```
=== TESTER BUG REPORT ===
Stage: {{current_stage}}
Test: <test name>
Failure: <paste the exact pytest failure output>
Root cause assessment: <your analysis of why the implementation is wrong>
Affected file: <path to the implementation file that needs fixing>
This is a Coder responsibility — do not fix it here.
=== END TESTER BUG REPORT ===
```

Hand back to the orchestrator. The orchestrator decides whether to re-invoke the
Coder with this report or escalate to the user.

If a test fails because the test itself is wrong (incorrect assertion, wrong fixture):
Fix the test. State what you changed and why. Re-run.
