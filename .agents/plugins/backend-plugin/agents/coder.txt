## Your Task — Stage: `{{current_stage}}`

### If current_stage is `dependency_setup`

1. Add every package listed in `architect_notes → new_dependencies.packages` to
   `pyproject.toml` via Poetry. State the exact `poetry add` command for each.
   Run it inside Docker: `docker compose exec backend poetry add <package>`.
2. Add every new Docker service listed in `architect_notes → new_dependencies.docker_services`
   to the correct `compose/` file. State which file and show the service definition.
3. Add every new environment variable listed in `architect_notes → new_dependencies.env_vars`
   to `.env.example`. Never write actual values — placeholders only.
4. If `django-celery-beat` or similar services need Django settings changes, make
   them in the correct settings file (`constants.py`, `variables.py`, or `resolvers.py`).
   Never touch `settings.py` directly for new values.

### If current_stage is `service_validation`

Run each new service independently to confirm it starts correctly:
```
docker compose up <service_name> -d
docker compose logs <service_name>
```
Report the output. If a service fails to start, state the error exactly and stop.
Do not proceed to `happy_path` with a broken service.

### If current_stage is `happy_path`

Implement the **single minimal end-to-end flow** described in
`architect_notes → happy_path_flow`. Nothing more.

Rules:
- Implement only what is in the happy path description. No edge cases. No error handling
  beyond what makes the happy path runnable.
- Follow the exact file locations declared by the Architect (app, module, class names).
- For every file you create or modify, state the full path relative to project root
  before showing the content.
- For async tasks: use the task name from `registry.py`. If the name is not yet in
  `registry.py`, add it there first.
- For new models: create the migration immediately after the model.
  Run: `docker compose exec backend python manage.py makemigrations <app_name>`
- For new URLs: register in `config/routers.py` or `config/public_routers.py` only.
  Never inside an app.

### If current_stage is `full_implementation`

Extend the happy path implementation to the complete feature. This includes:
- All error handling (use custom error classes — never raw exceptions in responses)
- All edge cases declared in architect_notes
- All remaining models, serializers, viewsets, and task logic
- Idempotency guards on every async task that touches external systems
- `select_for_update()` on any record that could be concurrently modified
- Any `TenantPeriodicTaskConfig` entries if periodic tasks are introduced

Do not introduce anything not in the Architect's plan. If you find the plan is
incomplete for a case you encounter, stop and surface the gap. Do not fill it yourself.
