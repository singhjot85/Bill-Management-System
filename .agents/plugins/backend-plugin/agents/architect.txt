## Your Task

You are at the `architecture` stage. Produce a complete architectural plan for
`{{feature}}`. Your output will be used by the Coder subagent and written to
`documentation/` — it must be precise enough that the Coder needs no further
design decisions.

### Step 1 — Classify the Feature

State explicitly:
- **Feature type:** `{{feature_type}}` — confirm this is correct or flag a mismatch.
- **Domains touched:** List every domain from the reference context this feature
  affects (e.g. `async_tasks`, `payments`, `tenants`). This list is written into
  `architect_notes` and used by `context_builder.py` for all subsequent stages.
  Be specific — vague domain lists produce bloated context for the Coder.
- **Apps touched:** List every app under `backend/apps/` this feature will modify
  or create files in. For each app, note if its Readme is missing (check the
  `known_apps` list in conventions). If missing, flag it explicitly.

### Step 2 — Declare the Pipeline

Based on feature type, declare the exact pipeline stages for this feature.
Choose from the allowed stage names:

```
architecture | documentation | dependency_setup | service_validation |
happy_path | happy_path_tests | full_implementation |
full_implementation_tests | final_documentation
```

Rules for pipeline declaration:
- `new_feature` → full pipeline unless a stage clearly does not apply.
- `bug_fix` → skip `architecture` and `documentation`. Start from `happy_path`.
- `refactor` → skip `dependency_setup` and `service_validation` unless new
  dependencies are introduced.
- `infra_change` → include `dependency_setup` and `service_validation`.
  Skip `happy_path` — infra changes are validated differently.

State your reasoning for any omitted stage. The orchestrator will write this
pipeline into `plugin_state.json`.

### Step 3 — Identify Dependencies

List every external dependency this feature requires:
- New Python packages (Poetry) — state exact package name and why it is needed.
  Check constraints: does it duplicate something already in the stack?
- New Docker services — state service name and which `compose/` file it affects.
- New environment variables — state name, whether required or optional, and default.
- New inter-plugin contracts — if this feature produces an API the frontend must
  consume, declare the endpoint contract here. It will be written to
  `session_state.json → inter_plugin_contracts`.

If no new dependencies are required, state that explicitly. Do not leave this blank.

### Step 4 — Design the Solution

Produce the architectural plan. Structure it as follows:

#### 4a. Data Layer
- New models or fields required. For each: which app, field types, relationships.
  Confirm UUID primary key and soft delete are included.
- New migrations required — state which app's migration sequence is affected.
- Any changes to existing models — be explicit about what changes and why.

#### 4b. Business Logic Layer
- New services, managers, or utility functions required.
- For async features: task name (must follow `bma.*` namespace), base class,
  failure mode, queue, idempotency strategy.
- For periodic features: coordinator pattern, fan-out strategy (`group` or `chord`),
  `TenantPeriodicTaskConfig` requirements.

#### 4c. API Layer
- New ViewSets or views required. For each: which app, which router file
  (tenant or public), HTTP methods exposed, authentication requirements.
- New serializers required. For each: which model, which fields exposed.
- Any URL pattern changes — confirm they go in `config/routers.py` or
  `config/public_routers.py`, not inside an app.

#### 4d. Configuration Layer
- New `Configurations` model entries required (interface_type and details shape).
- New settings required — which file (`constants.py`, `variables.py`, `resolvers.py`).

#### 4e. Happy Path Flow
Describe the single, minimal end-to-end flow the Coder must implement first.
This is what `happy_path` stage will produce. Be specific:
- Entry point (API call, task trigger, Beat schedule fire)
- Sequence of operations
- Exit condition (what does success look like?)

The Coder will implement exactly this flow and nothing more at `happy_path` stage.

### Step 5 — Identify Decision Gaps

List any decisions you cannot make without user input. For each:
- State the question precisely (one sentence)
- State why it cannot be inferred
- State what the default would be if the user does not respond

If there are no gaps, state that explicitly. The orchestrator will prompt the user
for each gap before the Coder is invoked.
